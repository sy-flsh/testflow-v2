## 2. 프로젝트 개요 (Project Overview)

### 2.1 목적

TMS(Test Management System)는 소프트웨어 테스트 활동을 체계적으로 관리하기 위한 **테스트 관리 도구**입니다. 본 프로젝트는 다음을 목표로 합니다.

- 테스트 케이스/스위트의 작성·버전 관리 및 재사용성 확보
- 테스트 계획·실행(테스트 런)·결과 기록의 추적성 확보
- 결함(Defect) 등록·추적 및 테스트 케이스와의 연계 관리
- 테스트 커버리지/진척/품질 지표의 가시화 및 리포팅
- 다수 이해관계자(QA, 개발, PM)가 협업하는 환경에서의 데이터 일관성 확보

### 2.2 범위

| 구분 | 포함 | 비고 |
| --- | --- | --- |
| Backend | API 서버, 도메인 로직, 데이터 영속화, 인증/인가 | 영역별 기술 스택은 Backend 정의서에서 명시 |
| Frontend | 사용자 화면(UI), 상태 관리, API 연동 | 영역별 기술 스택은 Frontend 정의서에서 명시 |
| QA | 테스트 전략, 자동화 테스트, 품질 게이트 | 테스트 도구는 QA 정의서에서 명시 |
| 공통 인프라 | CI/CD, 로깅/모니터링, 시크릿 관리 | 본 문서에서 공통 원칙만 정의 |

### 2.3 주요 이해관계자 (Stakeholders)

| 역할 | 책임 |
| --- | --- |
| PM | 전체 표준 정의, 우선순위 조정, 일정/범위 관리 |
| 기능 기획자(Feature Planner) | 사이트 기능 정의·정리(기능 명세), 수용 기준 도출 및 기능 정의서 작성 |
| Backend 개발 | 서버/도메인/데이터 계층 구현 및 백엔드 정의서 작성 |
| Frontend 개발 | UI/UX 구현 및 프론트엔드 정의서 작성 |
| QA | 품질 보증, 테스트 자동화, 결함 관리 |
| DBA | DB 물리 설계, 마이그레이션 검토/승인, 성능 튜닝, 백업/복구, DB 보안 및 DBA 정의서 작성 |
| 운영(Ops) | 배포, 모니터링, 장애 대응 |
| 제품/현업 사용자 | 요구사항 제공, 사용자 검증(UAT) |

## 3. 공통 명명 규칙 원칙 (Naming Convention Principles)

세부 케이스 표기(클래스/변수/컴포넌트/파일 등)는 L1 정의서가 정합니다. 본 절은 전 영역이 공유해야 할 **명명의 상위 원칙**만 규정합니다.

### 3.1 핵심 원칙

| 원칙 | 설명 |
| --- | --- |
| 의미 기반 명명 | 이름은 역할/의도를 드러내야 한다. `data`, `temp`, `flag` 같은 모호한 이름 금지 |
| 검색 가능성 | 코드베이스에서 검색 가능한 충분한 길이의 명확한 이름을 사용한다 |
| 일관성 | 동일 개념은 전 영역에서 동일 용어로 표현한다 (용어 사전 준수) |
| 발음 가능성 | 사람이 읽고 말할 수 있는 이름을 사용한다 |
| 부정/이중 부정 회피 | `isNotInvalid` 처럼 혼란스러운 부정형을 피한다 |

### 3.2 약어 사용 정책

| 정책 | 설명 |
| --- | --- |
| 표준 약어만 허용 | 업계 통용 약어(`id`, `url`, `http`, `db`, `api`)만 사용 |
| 도메인 약어 사전화 | 프로젝트 고유 약어는 반드시 용어 사전에 등록 후 사용 |
| 임의 축약 금지 | `usr`, `cnt`, `mng` 등 임의 축약 금지 |
| 일관 표기 | 약어의 대소문자 표기는 영역 내 일관되게 (예: `Id` vs `ID` 중 택1, L1에서 확정) |

### 3.3 공통 용어 사전 (Ubiquitous Language)

도메인 핵심 용어는 한/영 매핑을 통일하여 백엔드 클래스명, 프론트엔드 컴포넌트명, API 경로, DB 테이블, 테스트 명세가 동일 용어를 사용하도록 한다. 용어 사전은 `docs/glossary.md`(권장)에서 관리하며, 신규 용어 추가 시 PM 합의를 거친다.

| 한국어 | 영어 표준 | 약어(허용 시) |
| --- | --- | --- |
| 테스트 케이스 | TestCase | TC |
| 테스트 스위트 | TestSuite | - |
| 테스트 실행(런) | TestRun | - |
| 결함 | Defect | - |
| 사용자 | User | - |

> 위 표는 시드(seed)이며, 도메인 확정에 따라 PM 주도로 지속 갱신한다. 전체 용어는 `docs/glossary.md`를 정본으로 한다.

### 3.4 불리언/컬렉션/시간 명명 가이드

| 대상 | 원칙 |
| --- | --- |
| 불리언 | `is/has/can/should` 등 술어형 접두어 사용 |
| 컬렉션 | 복수형 또는 `~List` 형태로 다수임을 드러냄 |
| 시간 값 | 의미와 단위를 포함 (`createdAt`, `expiresInSeconds`) |
| 식별자 | `~Id` 접미어로 식별자임을 명시 |

## 4. 디렉터리 / 패키지 구조 원칙 (Directory & Package Structure Principles)

### 4.1 모노레포 최상위 구조

영역별 코드는 명확히 분리하되, 공통 표준 문서는 단일 위치에서 관리한다.

| 경로 | 용도 |
| --- | --- |
| `/backend` | 백엔드 애플리케이션 |
| `/frontend` | 프론트엔드 애플리케이션 |
| `/docs` | 프로젝트 문서 (표준, 설계, 운영 가이드) |
| `/docs/standards` | 개발 표준 정의서 모음 |
| `/.github` 또는 CI 설정 | CI/CD 파이프라인 정의 |
| `/scripts` | 빌드/배포/운영 보조 스크립트 |

> 단일 저장소(모노레포)와 다중 저장소(폴리레포) 중 선택은 인프라 전략에 따른다. 본 문서는 구조 원칙을 제시하며, 어느 형태든 아래 원칙을 만족해야 한다.

### 4.2 레이어 분리 원칙 (공통)

전 영역은 **관심사 분리(Separation of Concerns)**를 준수한다. 구체 레이어 명칭과 책임은 L1에서 정의하되, 다음 상위 원칙을 따른다.

| 원칙 | 설명 |
| --- | --- |
| 단방향 의존 | 상위 계층 → 하위 계층 단방향 의존. 역방향/순환 의존 금지 |
| 표현/도메인/인프라 분리 | UI·API 표현 계층, 비즈니스 도메인 계층, 데이터·외부연동 인프라 계층을 분리 |
| 도메인 독립성 | 핵심 도메인 로직은 프레임워크/외부 라이브러리에 최소 의존 |
| 경계 명확화 | 계층 간 데이터 전달은 명시적 모델(DTO/모델 객체)로 수행 |

### 4.3 모듈화 기준

| 기준 | 설명 |
| --- | --- |
| 도메인 응집 | 기능/도메인 단위로 묶고, 기술 종류(util 모음 등)만으로 과도하게 분산하지 않는다 |
| 공개 인터페이스 최소화 | 모듈은 필요한 것만 외부에 노출하고 내부 구현은 캡슐화한다 |
| 폴더 = 책임 단위 | 디렉터리는 명확한 단일 책임을 갖는다 |
| 공통 코드 분리 | 영역 간 또는 모듈 간 공통 코드는 명시적 공통 영역으로 분리하고 무분별한 복제를 금지한다 |

## 5. 버전 관리 / 브랜치 전략 (Version Control & Branching)

### 5.1 브랜치 전략

기본 전략은 **Trunk 기반 + 단기 기능 브랜치**(GitHub Flow 변형)를 채택한다. 릴리스 케이던스가 길어지면 GitFlow로 전환을 검토한다.

| 브랜치 | 용도 | 규칙 |
| --- | --- | --- |
| `main` | 항상 배포 가능한 안정 브랜치 | 직접 푸시 금지, PR을 통해서만 머지 |
| `feature/<설명>` | 신규 기능 개발 | `main`에서 분기, 단기 유지 후 머지 |
| `fix/<설명>` | 버그 수정 | `main`에서 분기 |
| `hotfix/<설명>` | 운영 긴급 수정 | 우선 머지 및 즉시 배포 |
| `release/<버전>` | (선택) 릴리스 준비 | 정식 릴리스 분리가 필요할 때만 사용 |

**브랜치 운영 원칙**
- 브랜치는 짧게 유지하고 자주 머지하여 통합 비용을 줄인다.
- 브랜치명은 소문자, 케밥/슬래시 구분, 이슈 번호 포함을 권장한다. 예: `feature/TMS-123-testcase-search`.
- 머지 후 브랜치는 삭제한다.

### 5.2 커밋 메시지 컨벤션

**Conventional Commits** 형식을 표준으로 채택한다.

```
<type>(<scope>): <subject>

<body>

<footer>
```

| 요소 | 규칙 |
| --- | --- |
| type | `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`, `perf`, `ci` 중 하나 |
| scope | 변경 영역 (예: `backend`, `frontend`, `auth`). 선택적 |
| subject | 명령형, 50자 이내, 마침표 없이 |
| body | 변경 이유와 맥락(무엇을 했는지보다 왜 했는지). 선택적 |
| footer | 이슈 참조(`Refs: TMS-123`), Breaking Change 표기 |

**원칙**
- 하나의 커밋은 하나의 논리적 변경 단위로 제한한다.
- 빌드/테스트가 통과하지 않는 상태를 커밋하지 않는다(WIP은 로컬에서만).
- **커밋 메시지 subject는 "수정한 내용을 분석해 한 줄로 요약"**한다. 무엇을 바꿨는지가 한눈에 드러나도록 명령형·간결하게 작성하고, `수정함`/`작업중`/`fix` 같은 의미 없는 메시지는 금지한다. 본문/푸터는 필요 시에만 덧붙인다.

### 5.3 버전 관리 (Versioning)

릴리스 버전은 **Semantic Versioning(`MAJOR.MINOR.PATCH`)**을 따른다.

| 자리 | 증가 조건 |
| --- | --- |
| MAJOR | 하위 호환을 깨는 변경 |
| MINOR | 하위 호환되는 기능 추가 |
| PATCH | 하위 호환되는 버그 수정 |

## 6. 코드 리뷰 및 PR 프로세스 (Code Review & PR Process)

### 6.1 PR 기본 규칙

| 규칙 | 내용 |
| --- | --- |
| PR 단위 | 작고 리뷰 가능한 크기(권장 변경 400라인 이하)로 분할 |
| PR 템플릿 | 변경 목적, 변경 사항 요약, 테스트 방법, 관련 이슈, 영향 범위, 스크린샷(UI) 포함 |
| 셀프 리뷰 | 작성자는 PR 생성 전 본인 diff를 먼저 검토 |
| CI 통과 | 모든 자동 검사(빌드/테스트/린트)가 통과해야 리뷰 요청 가능 |
| 최소 승인 | 최소 1인 이상 승인 필요. 핵심/위험 변경은 2인 이상 권장 |

### 6.2 리뷰 기준 (Review Checklist)

| 분류 | 확인 항목 |
| --- | --- |
| 정확성 | 요구사항을 충족하는가, 엣지 케이스를 처리하는가 |
| 가독성 | 명명/구조가 본 표준 및 L1 표준을 준수하는가 |
| 설계 | 레이어 분리/의존 방향/중복 제거 원칙을 지키는가 |
| 테스트 | 변경에 대응하는 테스트가 존재하고 충분한가 (QA 정의서 기준) |
| 보안 | 입력 검증, 인가, 시크릿 노출 여부를 점검했는가 |
| 성능 | 명백한 비효율(N+1, 불필요한 연산)이 없는가 |
| 문서 | 공개 API/주요 변경에 대한 문서/주석이 갱신되었는가 |

### 6.3 리뷰 에티켓

- 리뷰 코멘트는 코드에 대한 것이며 사람에 대한 것이 아니다.
- 변경 요구는 근거와 함께 제시하고, 단순 선호는 `nit:`으로 표기한다.
- 리뷰 응답/재요청은 빠르게(권장 1영업일 이내) 진행한다.

### 6.4 머지 정책

| 정책 | 내용 |
| --- | --- |
| 머지 방식 | Squash merge를 기본으로 하여 `main` 히스토리를 깔끔하게 유지 |
| 머지 전제 | CI 통과 + 필수 승인 + 미해결 리뷰 코멘트 없음 |
| 머지 권한 | 작성자 본인이 승인 충족 후 머지 (또는 자동 머지). 직접 `main` 푸시 금지 |
| 충돌 처리 | 머지 전 최신 `main`을 반영(rebase/merge)하여 충돌 해소 |

| 항목 | 내용 |
| --- | --- |
| 개요 | 프로젝트/모듈의 목적 |

### 7.3 주석 정책

| 원칙 | 설명 |
| --- | --- |
| Why 중심 | 코드가 "무엇을" 하는지가 아니라 "왜" 그렇게 했는지를 설명한다 |
| 자기 문서화 우선 | 좋은 명명/구조로 주석 필요성을 최소화한다 |
| 공개 API 문서화 | 외부에 노출되는 함수/모듈은 시그니처 수준의 문서 주석을 작성한다 (형식은 L1에서 규정) |

## 8. 품질 기준 (Quality Standard)

세부 테스트 작성 규칙과 커버리지 측정 도구는 QA 정의서(`test-standard.md`)에서 구체화한다. 본 절은 전 영역이 만족해야 할 품질 게이트의 상위 기준을 정의한다.

### 8.1 테스트 커버리지 목표

| 영역 | 라인/구문 커버리지 목표 | 비고 |
| --- | --- | --- |
| Backend 핵심 도메인 로직 | 80% 이상 | 비즈니스 규칙은 우선순위 최상 |
| Backend 전체 | 70% 이상 | 단순 위임/설정 코드는 예외 가능 |
| Frontend 로직(상태/유틸) | 70% 이상 | 순수 UI 마크업은 예외 가능 |
| 신규/변경 코드 | 80% 이상 | PR 단위 신규 코드에 강하게 적용 |

> 위 수치는 기준 기본값이며, QA 정의서에서 도구/예외 규칙과 함께 최종 확정한다. 커버리지는 목표일 뿐 맹신하지 않으며, 의미 있는 테스트를 우선한다.

### 8.2 정적 분석 기준

| 기준 | 내용 |
| --- | --- |
| 린터/포매터 | 영역별 표준 린터/포매터를 CI에서 강제 (구체 룰은 L1) |
| 빌드 경고 | 신규 경고 0건 유지(Treat warnings as errors 권장) |
| 취약점 스캔 | 의존성 취약점 스캔을 CI에 포함, 심각도 High 이상은 머지 차단 |
| 코드 복잡도 | 과도한 함수 길이/순환 복잡도는 리뷰에서 분할 요구 |
| 중복 코드 | 정적 분석 또는 리뷰로 중복을 식별하고 제거 |

### 8.3 품질 게이트 (Definition of Done)

작업이 "완료"로 인정되기 위한 공통 조건이다.

- 요구사항/인수 조건을 충족한다.
- 본 표준 및 해당 L1 표준을 준수한다.
- 신규/변경 로직에 대응하는 테스트가 통과한다.
- CI(빌드/테스트/린트/보안 스캔)가 모두 통과한다.
- 최소 승인 수의 코드 리뷰를 통과한다.
- 관련 문서/주석이 갱신되었다.

## 9. 보안 / 로깅 / 에러 처리 공통 원칙 (Security, Logging, Error Handling)

### 9.1 보안 공통 원칙

| 원칙 | 설명 |
| --- | --- |
| 입력 신뢰 금지 | 모든 외부 입력은 검증/정제 후 사용한다 (서버 측 검증 필수) |
| 최소 권한 | 사용자/서비스/토큰은 필요한 최소 권한만 부여한다 |
| 인증과 인가 분리 | 인증(누구인가)과 인가(무엇을 할 수 있는가)를 명확히 구분한다 |
| 시크릿 비저장 | 비밀번호/키/토큰을 코드·저장소·로그에 남기지 않는다 (시크릿 매니저/환경변수 사용) |
| 전송/저장 암호화 | 통신은 TLS, 민감 데이터는 저장 시 암호화한다 |
| 민감정보 마스킹 | 개인정보/인증정보는 로그/응답에서 마스킹한다 |
| 의존성 관리 | 의존성 취약점을 주기적으로 점검하고 갱신한다 |
| 방어적 기본값 | 권한/노출은 기본 차단(deny by default)으로 설정한다 |
| 워크스페이스 격리 | 모든 데이터는 워크스페이스(Workspace) 경계로 격리하고, 서로 다른 워크스페이스 간 데이터 접근을 금지한다. 격리 구현(공유 스키마 + `workspace_id` 등)은 L1에서 정의한다 |

### 9.2 로깅 공통 원칙

| 원칙 | 설명 |
| --- | --- |
| 구조화 로깅 | 기계 파싱 가능한 구조화 형식(JSON 등)을 사용한다 |
| 로그 레벨 | `ERROR/WARN/INFO/DEBUG`를 의미에 맞게 사용한다 |
| 상관관계 ID | 요청 추적을 위한 Correlation/Trace ID를 전 구간에 전파한다 |
| 민감정보 제외 | 개인정보/시크릿/인증 토큰을 로그에 기록하지 않는다 |
| 맥락 포함 | 무엇이/언제/어디서 발생했는지 맥락(식별자, 타임스탬프)을 포함한다 |
| 과도 로깅 금지 | 노이즈를 줄이고 의미 있는 이벤트 중심으로 기록한다 |

**로그 레벨 사용 기준**

| 레벨 | 용도 |
| --- | --- |
| ERROR | 즉시 대응이 필요한 실패, 기능 중단 |
| WARN | 비정상이나 복구 가능, 잠재 위험 |
| INFO | 주요 비즈니스 이벤트/상태 전이 |
| DEBUG | 개발/진단용 상세 정보 (운영 기본 비활성) |

### 9.3 에러 처리 공통 원칙

| 원칙 | 설명 |
| --- | --- |
| 명시적 처리 | 예외/에러를 무시(silent catch)하지 않고 명시적으로 처리하거나 전파한다 |
| 예측 가능한 응답 | 사용자/클라이언트에는 일관된 에러 형식으로 응답한다 (구체 포맷은 L1) |
| 내부 정보 비노출 | 스택트레이스/내부 구조를 외부 응답에 노출하지 않는다 |
| 사용자 친화 메시지 | 외부 메시지는 안전하고 이해 가능하게, 상세 원인은 로그에 기록한다 |
| 실패 격리 | 부분 실패가 전체 장애로 번지지 않도록 경계를 둔다 (타임아웃/재시도/폴백) |
| 데이터 일관성 | 실패 시 일관성을 보존한다 (트랜잭션/보상 처리) |

**공통 에러 응답 원칙(상위)**: 클라이언트 응답은 최소한 (1) 식별 가능한 에러 코드, (2) 안전한 메시지, (3) 추적용 상관관계 ID를 포함해야 한다.

- **단일 공용 응답 래퍼**: 성공/실패 응답은 동일한 공용 응답 래퍼(`success`/`code`/`message`/`data`)를 공유하고, 에러 시에는 진단 필드(`traceId`/`timestamp`/`path`/`errors`)를 **추가**한다.
- **에러 코드 표기**: 에러 코드는 도메인명을 보존한 **문자열 의미 코드**(`{DOMAIN}_{상황}`, 예: `TESTCASE_NOT_FOUND`)로 하여 자기설명적이고 로그 추적이 쉽게 한다.
- 구체 스키마(필드 타입·직렬화·매핑)는 Backend/Frontend 정의서가 위 원칙에 맞춰 확정한다.

| --- | --- | --- | --- |
| 3. 명명 규칙 원칙 | 클래스/메서드/DB/URI 명명 구체화 | 컴포넌트/파일/CSS 명명 구체화 | 테스트 명명 구체화 |
| 4. 구조 원칙 | 패키지/레이어 구조 | 폴더/컴포넌트 구조 | 테스트 디렉터리 구조 |
| 5. 버전 관리 | 그대로 준수 | 그대로 준수 | 그대로 준수 |
| 6. 리뷰/PR | 그대로 준수 | 그대로 준수 | 테스트 포함 여부 검증 |
| 7. 문서화 | API 문서/주석 구체화 | 컴포넌트 문서/주석 구체화 | 테스트 리포트 기준 |

| 9. 보안/로깅/에러 | 서버 측 구체 규칙 | 클라이언트 측 구체 규칙 | 보안/에러 시나리오 테스트 |

> **DBA 참조**: DBA 에이전트는 §4(구조)·§8(품질)·§9(보안)를 근거로 물리 스키마/마이그레이션/성능/백업/DB 보안을 구체화한다. 단, DB 명명·ORM·워크스페이스 격리·ERD 등 Backend가 정한 항목은 **재정의하지 않고 참조**한다(중복 금지, dba-standard §1).

**불일치 처리 절차**: L1 작성 중 본 문서와 충돌하거나 본 문서가 모호하다고 판단되면, 임의 해석하지 말고 PM에게 변경/명확화를 요청한다. 본 문서가 갱신되면 L1 정의서도 정합성을 재검토한다.
